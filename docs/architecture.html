Архитектура qStack

Распределённая система с полной микросервисной архитектурой. Каждый компонент — независимый сервис со своим go.mod, бинарником, схемой базы данных и развёртыванием.

Monorepo Layout

qStack/
qStack/
├── pkg/                       # Shared SDK (types, gRPC protos, helpers)
│   ├── types/                 # Shared domain types
│   ├── grpc/                  # gRPC service definitions + generated code
│   ├── nats/                  # NATS helpers (connect, publish, subscribe)
│   ├── ca/                    # Internal PKI (cert signing, rotation)
│   └── config/                # Shared config types
├── services/                  # Microservices (each has own go.mod)
│   ├── api/                   # qstack-api (Gateway, Auth, Dashboard)
│   ├── compute/               # qstack-compute (VMs, Hosts, Scheduler, HA)
│   ├── storage/               # qstack-storage (Pools, Volumes, Snapshots)
│   ├── network/               # qstack-network (Networks, IPAM, DHCP)
│   ├── image/                 # qstack-image (Images, Builds, Cache)
│   ├── billing/               # qstack-billing (Meter, Invoice, Quota)
│   ├── backup/                # qstack-backup (Backup, Restore, Verify)
│   └── ai/                    # qstack-ai (Advisor, Predictor, AutoHeal)
├── agent/                     # qstack-agent (Hypervisor agent)
├── dashboards/                # Web UIs (strictly separated, PCI-DSS)
│   ├── admin/                 # qstack-admin (operator)
│   └── user/                  # qstack-user (tenant)
├── configs/                   # YAML examples
├── docker-compose.yml         # Local dev (all services + infra)
├── k8s/                       # Kubernetes manifests
│   ├── common/                # namespace, postgres, nats, cert-manager, glitchtip
│   └── {api,compute,storage,...}/
├── go.work                    # Monorepo workspace
├── Makefile
└── proto/                     # Protobuf definitions (shared)

Принципы микросервисов

  • Собственная кодовая база — каждый сервис имеет свой go.mod, Dockerfile и сборку
  • Собственная DB схема — PostgreSQL schemas per service (compute_schema, storage_schema). Сервисы читают/пишут только свои таблицы
  • Нет общего internal кода — общий код в pkg/ (SDK). Domain types через gRPC protos
  • gRPC для синхронных вызовов — service-to-service через генерируемые gRPC клиенты (mTLS)
  • NATS для асинхронных — event-driven коммуникация через NATS (NKey + TLS)
  • Sagas для транзакций — мульти-сервисные операции (создание VM) через Sagas
  • Независимый деплой — deploy, scale, rollback каждого сервиса независимо
  • API Gateway — единственный сервис с внешними REST endpoint. Все остальные экспонируют только gRPC

PCI-DSS Requirements:
Req 7 — Ограничение доступа к компонентам системы только тем, кому это нужно по работе.
Req 8 — Идентификация и аутентификация (MFA для admin).
Req 10 — Отслеживание и мониторинг всего доступа.

Паттерн Saga

Мульти-сервисное создание VM через Saga в API Gateway:

1. API получает POST /v1/vms 2. API создаёт запись Saga (status: "in_progress") 3. → Storage.CreateVolume() [при ошибке: компенсация ничего, возврат ошибки] 4. → Network.AllocateIP() [при ошибке: компенсация Storage.DeleteVolume(), возврат] 5. → Compute.CreateVM() [при ошибке: компенсация Network.ReleaseIP() + Storage.DeleteVolume()] 6. → Image.CacheToHost(vm_host) [async, best effort — VM может загрузиться без кеша] 7. Saga status: "completed" State machine: created → running → completed | compensating → compensated | failed

High Availability

PostgreSQL HA (Patroni)

Один PostgreSQL — единственная точка отказа. Для production:

Patroni (3 nodes) → автоматический failover, синхронная репликация ├── Primary (read/write, все сервисы подключаются сюда) ├── Replica 1 (read-only, автоматический promotion) └── Replica 2 (read-only, автоматический promotion) Connection pooling: PgBouncer (или PgPool-II) перед Patroni
